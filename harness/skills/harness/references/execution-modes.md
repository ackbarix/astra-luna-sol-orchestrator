## 1. 모드 A: 워크플로 조율

`als-flow run SCRIPT.py`로 Python 조율 스크립트를 실행한다. 분산 실행(팬아웃), 반복, 조건 분기와 같은 제어 흐름을 모델이 그때그때 판단하지 않고 **코드**가 정한다. 따라서 같은 입력을 주면 같은 구조로 재현하기 쉽고, 많은 에이전트를 병렬로 실행하기에도 알맞다.

```
[메인 에이전트] → als-flow run scripts/{name}.py
           ├── flow.phase('탐색'): flow.pipeline(items, lambda item: flow.agent(...))
           ├── flow.phase('검증'): 발견한 항목마다 반박할 근거를 찾아 검증(병렬)
           └── flow.done({'confirmed': ...})   ← 구조화된 최종 결과
```

**주요 기능:**
- `Flow(name=..., phases=[...], workdir='.', budget_tokens=None, concurrency=4)` — 실행 하나를 정의한다. `concurrency`는 최대 6이다.
- `flow.agent(prompt, agent_type=None, schema=None, label=None, model=None, effort=None, sandbox=None, cwd=None, timeout=1800)` — 서브에이전트를 실행한다. `schema`에 JSON 스키마(JSON Schema)를 지정하면 파싱된 JSON을 반환한다. `agent_type`을 지정하면 `.codex/agents/`(또는 `$CODEX_HOME/agents/`)에 정의된 사용자 정의 유형을 쓸 수 있다. `model`, `effort`, `sandbox`는 `agent_type` 없이 호출할 때만 쓸 수 있다. 사용자 정의 유형의 모델과 권한은 그 TOML 정의가 정하기 때문이다. `cwd`로 다른 작업 디렉터리(예: 미리 만든 git worktree)에서 실행해 파일 변경을 격리한다.
- `flow.pipeline(items, fn)` — 각 항목이 `fn` 안의 여러 단계를 독립적으로 거친다. 항목 사이에 동기화 장벽이 없으므로 **다단계 작업에서는 기본으로 사용한다.**
- `flow.parallel(thunks)` — 모든 작업이 끝날 때까지 기다리는 동기화 장벽이다. 다음 단계에서 이전 단계의 결과 **전체**가 필요할 때만 쓴다. 중복 제거 또는 전체 개수를 기준으로 한 조기 종료가 이에 해당한다.
- `with flow.phase(title):` / `flow.log(msg)` — 진행 상황을 묶어서 표시하고 사용자에게 현재 작업을 알린다.
- `flow.budget_remaining()` — 사용자가 지정한 토큰 예산(예: "+500k")을 `budget_tokens`로 넘겼을 때 남은 양을 알려 준다. 작업 규모를 동적으로 조절할 때 쓴다.
- `flow.done(result)` — 구조화된 최종 결과를 메인 에이전트에 넘긴다.

**특징:**
- 코드가 제어 흐름을 정하므로 같은 입력이면 같은 실행 구조를 따른다.
- 구조화 출력(`schema`)을 사용하므로 단계 사이에 스키마에 맞는 데이터를 전달할 수 있다.
- `als-flow run SCRIPT.py --resume RUN_ID`로 중단한 실행을 이어 갈 수 있다. 바뀌지 않은 `flow.agent()` 호출은 `_workspace/.flow/<run_id>/`에 캐시된 결과를 즉시 반환하므로 일부만 다시 실행할 때 드는 비용이 적다.
- `als-flow status`와 `als-flow ls`로 실행 상태와 이전 실행 목록을 확인한다.

**제약 사항:**
- **사용자가 먼저 요청해야 한다.** 모델 호출을 대량으로 쓰기 때문이다. 사용자가 워크플로나 여러 에이전트의 조율을 직접 요청했거나, `als-flow` 실행을 명시한 스킬을 실행한 경우에만 쓸 수 있다. 하네스가 만든 조율 스킬은 두 번째 경우에 해당한다. 다만 기본 에이전트 수는 적게 잡고, 대규모 분산 실행은 사용자가 명시적으로 요청했을 때만 사용한다.
- 프롬프트에 현재 시각(`time.time()`, `datetime.now()`)이나 난수(`random`)를 넣지 않는다. 프롬프트가 실행마다 달라지면 캐시가 맞지 않아 재개할 때 모든 호출을 다시 실행한다. 타임스탬프는 입력 파일로 전달한다.
- `Flow(...)`의 `name`과 `phases`에는 리터럴만 쓴다. 실행마다 바뀌는 값을 넣으면 실행을 식별하고 재개하기 어려워진다.
- 동시에 실행할 수 있는 에이전트 수는 `concurrency`(최대 6)로 제한된다. 상한을 넘은 작업은 자동으로 대기열에 들어간다. 한 실행에서 호출할 수 있는 전체 에이전트 수도 1,000건으로 제한해 과도한 실행을 막는다.
- 실패했거나 건너뛴 `flow.agent()`는 `None`을 반환한다. `flow.parallel()`은 호출이 실패해도 예외를 던지지 않으므로 결과에 반드시 `[r for r in results if r is not None]`을 적용한다.
- 하위 에이전트는 다시 위임할 수 없고(`max_depth = 1`), 워크플로를 다른 워크플로 안에서 중첩해 부르는 기능은 없다. 계층이 필요하면 한 스크립트의 `phase`로 평탄화한다.
- `flow.parallel()` 장벽은 작업이 끝나는 시점을 맞출 뿐 끝난 뒤의 수정은 막지 않는다. 혼합 모드에서는 워크플로 단계가 끝난 뒤 `als-agent send`로 깨운 이름 있는 에이전트가 그 단계의 산출물 파일을 고칠 수 있으므로, 모드가 바뀌는 경계에서 산출물을 동결한다(`orchestrator-template.md` 템플릿 B의 4단계).

**잘 맞는 작업:** 파일 N개 또는 관점 M개처럼 목록을 미리 정할 수 있는 분산 실행, 새 항목이 없을 때까지 반복하는 방식(Loop-until-dry)과 적대적 검증, 대규모 전환·감사, 구조화된 보고서 생성

**맞지 않는 작업:** 대화를 이어 가며 작업 대상을 찾아야 해서 목록을 미리 정할 수 없는 일, 중간에 사용자와 자주 상의해야 하는 일

> 구체적인 스크립트 기본 틀과 주의할 점은 `workflow-recipes.md`를 참고한다.

## 2. 모드 B: 지속형 에이전트 협업

이름을 붙인 에이전트를 `als-agent start`로 실행하고, 공유 작업 목록(`als-task`)과 `als-agent send`로 조율한다. 명시적인 팀 객체를 만들지 않으며, 이름을 붙여 실행한 에이전트가 하나의 협업 그룹이 된다.

```
[메인 에이전트(리더)]
    ├── als-agent start researcher --type researcher "역할 + 작업 지시 + 산출 경로"
    ├── als-agent start critic --type critic "..."
    ├── als-task add (작업 + 의존성) → 공유 작업 목록(_workspace/tasks.json)
    ├── als-agent send researcher "..."  ← 대화 맥락을 유지한 채 추가 지시
    └── als-agent list / show로 상태 확인 → 결과를 모음 → 최종 정리
```

**주요 기능:**
- `als-agent start NAME --type AGENT_TYPE "지시"` — `NAME`을 붙여 실행하면 `als-agent send`로 다시 부를 수 있는 지속형 에이전트가 된다. `AGENT_TYPE`은 `.codex/agents/`의 사용자 정의 유형이다.
- `als-agent send NAME "메시지" [--from OTHER]` — 앞서 실행한 에이전트가 **대화 맥락을 유지한 채** 작업을 이어 가게 한다. 결과를 주고받으며 반복해서 수정할 때 필요하다. 에이전트끼리 메시지를 전할 때는 `--from`에 보내는 쪽 이름을 적는다.
- `als-agent list` / `als-agent show NAME` — 실행 중인 에이전트와 각 에이전트의 상태·최근 응답을 확인한다.
- `als-task add` / `als-task update` / `als-task list` — 작업 목록을 공유한다(`_workspace/tasks.json`). 작업 사이의 의존 관계와 진행 상태를 관리하고, 감독자가 진행 상황에 따라 작업을 배정할 때 쓴다.

**특징:**
- 에이전트가 이전 대화와 작업 내역을 기억하므로 "같은 세션에서 앞서 만든 초안의 2절만 고쳐 줘"와 같은 후속 요청을 처리할 수 있다.
- 에이전트끼리 발견한 내용을 공유하고, 서로 다른 의견을 논의하며, 작업 방향을 바로 수정할 수 있다.
- 세션이 유지되는 동안 같은 전문 에이전트를 계속 활용할 수 있다.

**제약 사항:**
- 메인 에이전트(리더)가 직접 조율하므로 에이전트가 많을수록 리더에게 작업이 몰린다. 에이전트 수는 3~5명이 적당하다. 동시에 실행하는 수는 6을 넘지 않는다.
- 하위 에이전트는 다시 위임하지 않는다(`max_depth = 1`). 위임은 리더 한 단계에서만 한다.
- 서브에이전트를 한 번만 호출할 때보다 토큰이 더 많이 든다.
- 이름 있는 에이전트는 완료를 보고한 뒤에도 메시지를 받으므로, 다른 에이전트의 뒤늦은 질문에 답하다가 이미 넘긴 산출물을 고칠 수 있다. 다음 단계가 그 산출물을 읽는다면 단계 경계에서 산출물을 동결한다. 동결 절차는 `orchestrator-template.md` 템플릿 B의 4단계에 있다.

**잘 맞는 작업:** 작성자와 검증자가 결과를 주고받으며 반복해서 수정하는 일, 서로 맞지 않는 데이터를 논의해 하나로 합치는 일, 감독자가 진행 상황에 따라 작업을 배정하는 일, 세션 내내 전문 에이전트가 필요한 일

**맞지 않는 작업:** 결과만 받으면 되는 일회성 작업, 작업 목록을 미리 정할 수 있는 대규모 분산 실행

## 3. 모드 C: 서브에이전트 위임

Codex의 `spawn_agent` 도구를 한 번 호출해 서브에이전트에 맡기는 방식이다. 결과만 메인 에이전트에 돌아오며 에이전트끼리 통신하지 않는다.

```
[메인 에이전트] → spawn_agent(agent_type: A) ─┐
                → spawn_agent(agent_type: B) ─┼→ (한 턴에 병렬 실행, 최대 6) → 완료 결과를 모음
                → spawn_agent(agent_type: C) ─┘
```

**특징:**
- 실행 부담이 적고 빠르다. 메인 에이전트는 요약된 결과를 받는다.
- 서로 독립적인 호출을 **한 턴에 묶어** 보내면 동시에 실행된다. 동시 실행 상한은 `agents.max_concurrent_threads_per_session`(6)이다.
- 메인 에이전트는 이미 위임한 검색을 다시 수행하지 않고 결과를 기다린다.

**제약 사항:**
- 에이전트끼리 통신할 수 없고, 하위 에이전트가 다시 위임할 수도 없다(`max_depth = 1`).
- 결과를 받은 뒤 같은 에이전트와 대화를 이어 가야 한다면 처음부터 모드 B(`als-agent start`)로 실행한다.
- 모든 조율은 메인 에이전트가 맡는다.

**잘 맞는 작업:** 한 번으로 끝나는 조사·수집, 필요한 전문가를 골라 결과만 받는 작업, 한 차례의 독립 검증

**맞지 않는 작업:** 결과를 주고받으며 반복해서 수정해야 하는 일, 실행 흐름을 미리 정할 수 있는 대규모 분산 작업

## 4. 실행 모드를 고르는 결정 트리

```
작업 목록·검증 기준·반복 조건을 미리 코드로 표현할 수 있는가?
├── 예 → 워크플로 조율(모드 A)
│        제어 흐름을 모델이 판단하지 않고 코드로 정한다.
│        단, 사용자가 먼저 요청해야 한다는 조건을 지키고 에이전트 수를 필요 이상으로 늘리지 않는다.
│
└── 아니요 → 결과를 반복해서 주고받고 대화 맥락을 이어 가야 품질이 높아지는가?
              ├── 예 → 지속형 에이전트 협업(모드 B)
              │
              └── 아니요 → 에이전트가 두 명 이상인가?
                            ├── 예 → 서브에이전트 병렬 위임(모드 C)
                            └── 아니요 → 서브에이전트 단일 호출(모드 C)
```

**혼합 모드 선택:** 단계마다 위 질문의 답이 다르면 실행 모드를 섞는다. 다음 조합을 주로 쓴다.

| 조합 | 구성 | 예시 |
|------|------|------|
| 워크플로 수집 → 지속형 통합 | A → B | 자료를 대량으로 나누어 수집한 뒤, 서로 맞지 않는 데이터를 팀이 논의해 합의 |
| 지속형 생성 → 워크플로 검증 | B → A | 팀이 초안을 만든 뒤, 발견한 항목마다 적대적 검증을 분산 실행 |
| 서브에이전트 사전 조사 → 워크플로 본 작업 | C → A | 메인 또는 서브에이전트가 작업 목록을 먼저 파악한 뒤, 그 목록을 입력 파일로 워크플로에 전달 |

**조율 전에 목록을 확인하는 원칙:** 워크플로를 시작하기 전에 파일 목록, 검토 대상, 조사 항목을 간단히 살펴보고 작업 목록을 확정한다. 실행 전에 작업 형태를 파악하면 스크립트가 단순해지고 불필요한 작업이 줄어든다.

## 5. 기존 ALS 구성 재사용

프로젝트의 `.codex/agents/`나 `$CODEX_HOME/agents/`에 ALS 0.5 이하가 설치한 범용 역할이 있거나, `$astra-luna-sol` 스킬이 있으면 새 역할을 만들기 전에 재사용 후보로 다룬다.

| 기존 역할 | 모델·effort | sandbox | 맡는 일 |
|---------|-----------|---------|--------|
| `als_explorer` | gpt-6-luna · `max` | read-only | 범위가 정해진 코드 탐색, 호출 경로·의존 관계 추적 |
| `als_researcher` | gpt-6-luna · `max` | read-only | 외부 API·프레임워크·버전 호환성 조사 |
| `als_worker` | gpt-6-luna · `max` | workspace-write | 범위가 정해진 일반 구현 |
| `als_tester` | gpt-6-luna · `max` | workspace-write | 기존 검사 실행과 간단한 재현 |
| `als_test_designer` | gpt-6-luna · `max` | workspace-write | 까다로운 회귀 테스트 설계와 실패 재현 |
| `als_hard_worker` | gpt-6.1-sol · `high` | workspace-write | 여러 구성 요소에 걸친 어려운 구현과 분석 |

|---------|---------|
| 범용 역할이 새 역할을 모두 포함한다 | 새로 만들지 않고 `agent_type`에 기존 역할 이름을 지정한다. |

| 일부 겹치지만 도메인을 의도적으로 특화했다 | 새 사용자 정의 유형을 만든다. 이름이 `als_`로 시작하지 않게 해 범용 역할과 구분한다. |
| `$astra-luna-sol` 스킬과 호출 조건이 겹친다 | 새 오케스트레이터의 `description`에 적용 범위와 제외 조건을 적어 두 스킬이 같은 요청에 동시에 선택되지 않게 한다. |

**재사용 절차:**
1. 기존 역할 TOML의 `description`, `model`, `model_reasoning_effort`, `sandbox_mode`를 읽고 새 역할과 비교한다.
2. 기존 역할을 확장할 때는 그 역할을 부르는 다른 오케스트레이터의 동작도 바뀔 수 있으므로 넓어진 역할을 `description`에 반영한다. ALS 설치기가 관리하는 파일(`$CODEX_HOME/agents/` 등)이면 다시 설치할 때 덮어쓰일 수 있으므로, 확장 내용을 `AGENTS.md` 변경 이력에 남기고 사용자에게 알린다.
3. 오케스트레이터의 에이전트 구성표에 재사용한 역할을 그대로 적는다.
4. 6단계 검증(구조 검증과 시험 실행)을 다시 수행하고 `AGENTS.md` 변경 이력에 기록한다.
